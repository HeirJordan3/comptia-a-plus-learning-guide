## What Is It?

Networks move information from one device to another.

That information may travel over Ethernet, Wi-Fi, DSL, or other network types. From IP’s point of view, the transportation method matters less than what is inside the packets.

**IP** stands for Internet Protocol.

A simple way to picture it:

- The network is the road
- IP is the truck
- TCP or UDP is the box on the truck
- Application data is what is packed inside the box

## Why Does It Matter?

Almost every networking topic in A+ builds on IP basics:

- Ports and protocols
- DNS and DHCP
- Web traffic
- Remote access
- Wireless troubleshooting

If IP, TCP, UDP, and ports feel confusing, the later networking lessons will be harder. This lesson gives you the mental model first.

## How It Works

### Encapsulation

Networking stacks information inside other information. That nesting is called **encapsulation**.

Receiving systems unwrap the layers. That is **decapsulation**.

Example of web traffic:

```text
Ethernet frame
 └── IP packet
      └── TCP segment
           └── HTTP data
```

A basic view of a frame:

- Header at the beginning
- Payload in the middle
- Trailer at the end

Inside the Ethernet payload, you may find an IP header and IP payload.  
Inside the IP payload, you may find TCP or UDP.  
Inside TCP or UDP, you may find application data such as HTTP.

### Multiplexing

TCP and UDP help devices send many different kinds of traffic at the same time.

That ability to handle multiple conversations at once is called **multiplexing**.

### TCP — Transmission Control Protocol

TCP is **connection-oriented**.

That means there is a formal setup and a formal teardown, similar to a phone call:

1. Dial and wait for an answer
2. Say hello
3. Have the conversation
4. Say goodbye and hang up

TCP is also described as **reliable delivery**.

Why?

- The receiver sends acknowledgments
- Damaged or missing data can be requested again
- Both sides can manage speed with **flow control**

Flow control means the receiver can effectively ask the sender to slow down or speed up based on what it can handle.

### UDP — User Datagram Protocol

UDP is **connectionless**.

There is:

- No formal setup
- No formal teardown
- No acknowledgments from the protocol itself
- No built-in retransmission
- No built-in flow control

That is why people call UDP **unreliable delivery**. The word “unreliable” here means the protocol itself does not confirm delivery. It does not mean the application is useless.

UDP’s advantage is low overhead. It can just send data with a best-effort approach.

### When Apps Prefer UDP

Real-time traffic often prefers UDP.

Examples:

- Voice over IP
- Live video

If a moment of sound or video is lost, the conversation cannot freeze, rewind, and replay that exact moment. It is often better to keep moving.

Other low-overhead examples include:

- DHCP
- TFTP

Sometimes the application itself handles reliability instead of UDP. Other times, such as with voice traffic, the app may simply continue and let users ask someone to repeat themselves.

### When Apps Prefer TCP

Some applications need confirmation that data arrived correctly.

Examples:

- HTTPS
- SSH

Those apps commonly use TCP so acknowledgments, retransmissions, and reliable delivery are handled by the transport protocol.

### IP Addresses

IP addresses identify devices on the network, similar to street addresses for houses.

When TCP or UDP data arrives at a server’s IP address, the operating system still needs to know which service should receive it.

### Port Numbers

A **port number** tells the system which service or application should process the data.

Think of rooms in a house:

- Bedroom
- Living room
- Kitchen

Servers may run many services at once, such as:

- Web server
- DNS
- File server
- Voice services

Each service listens on a port number so the right traffic goes to the right place.

When two devices communicate, these details usually matter:

1. IP address
2. TCP or UDP
3. Port number

Both sides use IP addresses and ports. The client also uses a port so the server can send replies back correctly.

### Non-Ephemeral Ports

Non-ephemeral ports are permanent or well-known port numbers used by services.

They are often in the range **0–1023**, but a service can use other ports too.

Examples of the idea:

- A web service may listen on a known port
- An email service may listen on a known port
- A file service may listen on a known port

Clients need to know that port so they can reach the service.

### Ephemeral Ports

Ephemeral ports are temporary client port numbers.

They are commonly chosen from **1024–65535**.

They are used for one communication flow. When the conversation ends, that temporary port is no longer needed. The next conversation can use a different random client port.

### Port Number Ranges

TCP and UDP port numbers each range from **0 to 65535**.

Important detail:

- TCP port 80 is not the same thing as UDP port 80
- The numbering schemes look similar, but they belong to different protocols

### Ports Are Not Security

Port numbers are reference numbers, not a security system.

Someone can still discover a service even if the port number was changed. Knowing a port helps communication. It is not the same as protecting a system.

### Example: One Client, Multiple Services

Imagine a client and a server talking at the same time:

| Service | Protocol / Port |
| --- | --- |
| Web | TCP 80 |
| Voice over IP | UDP 5004 |
| Email | TCP 143 |

Example addresses:

- Client: `10.0.0.1`
- Server: `10.0.0.2`

Each conversation may share the same source and destination IP addresses, but use different destination ports for each service.

The client side usually uses different random **source ports** for each conversation. Those are ephemeral ports.

```text
Client 10.0.0.1                     Server 10.0.0.2
------------------------------------------------------------
Source port (random)  --->  Destination TCP 80   (web)
Source port (random)  --->  Destination UDP 5004 (VoIP)
Source port (random)  --->  Destination TCP 143  (email)
```

This same basic process works on a local network or across the internet.

## Common Mix-Ups

### TCP vs UDP

- TCP = connection-oriented and reliable
- UDP = connectionless and low-overhead

“Unreliable” for UDP means no built-in delivery confirmation, not “never works.”

### IP Address vs Port

- IP address = which device
- Port = which service on that device

### Ephemeral vs Well-Known Ports

- Well-known / non-ephemeral = usually the service side
- Ephemeral = usually the temporary client side

### TCP Port 80 vs UDP Port 80

Same number, different protocols. They are not interchangeable.
