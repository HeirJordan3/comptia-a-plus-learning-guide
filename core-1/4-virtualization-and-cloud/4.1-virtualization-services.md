## What Is It?

A **hypervisor**, also called a Virtual Machine Manager, is the software that manages virtual machines.

It sits between the physical system and the VMs. It allocates CPU, memory, networking, and other resources while keeping VMs separated.

## Why Does It Matter?

Help desk and IT support technicians see virtualization services when:

- Users run VMs on a laptop or desktop
- Companies host many VMs on servers
- Desktops are delivered remotely through VDI
- Apps are deployed in containers instead of full VMs
- Security teams worry about isolating workloads

Understanding hypervisor types and containers helps you explain performance, networking, and security trade-offs.

## Real-World Analogy

Think of a hypervisor like a building manager.

The physical hardware is the building. Each apartment is a VM. The manager assigns electricity, space, and access rules so one apartment does not take over the whole building.

Containers are more like rooms inside one apartment that share the same kitchen and utilities, but still keep their own locked closets.

## How It Works

### Hypervisor Basics

```text
Virtual Machines (guest OS + apps)
                ↓
           Hypervisor
                ↓
         Physical Hardware
```

Each VM has its own guest operating system and applications. That means each VM needs CPU time, RAM, and disk space.

### Type 1 Hypervisor

A **Type 1** hypervisor runs directly on hardware.

It is also called a **bare-metal** hypervisor because there is no normal desktop OS underneath it. The hypervisor itself is the main system on the machine.

Examples:

- VMware ESXi
- Microsoft Hyper-V

Common in enterprise servers.

### Type 2 Hypervisor

A **Type 2** hypervisor is a **hosted** hypervisor.

It runs on top of a normal operating system such as Windows or macOS.

Examples:

- VMware Workstation
- Oracle VirtualBox
- Parallels Desktop

Once the VMs are running, Type 1 and Type 2 VMs can look similar. The difference is where the hypervisor sits:

| Type | Runs On | Common Name |
| --- | --- | --- |
| Type 1 | Directly on hardware | Bare-metal |
| Type 2 | On top of a host OS | Hosted |

### CPU Support

Many modern CPUs include hardware support for virtualization.

| Vendor | Feature Name |
| --- | --- |
| Intel | VT / Virtualization Technology |
| AMD | AMD-V |

This helps hypervisors run more efficiently.

### Resource Requirements

Because each VM includes a full OS and apps, you need enough:

- CPU cycles
- RAM
- Drive space

If you run several VMs at once, the physical host must be strong enough to support all of them together.

### Virtual Networking

Client-side hypervisors often create internal virtual networks.

Common options:

| Network Mode | Meaning |
| --- | --- |
| Shared / NAT | VM uses a separate internal subnet; hypervisor translates traffic to the outside network |
| Bridged | VM appears as another device on the local network with no NAT |
| Private / isolated | VM can communicate only with itself or selected systems |

This gives administrators control over whether a VM can reach the outside world.

### Security Concerns

Hypervisors are designed to isolate VMs, but security still matters.

#### VM Escape

**VM escape** is a serious concern. It means malware on one VM finds a hypervisor flaw and reaches other VMs on the same host.

That would break the isolation model. Significant real-world VM escape breaches have been rare, but developers treat this risk seriously.

#### Secure Each Guest OS

Treat every VM like a real standalone computer:

- Configure a firewall
- Install anti-malware
- Harden the OS

#### Untrusted Downloaded VMs

Attackers sometimes publish infected VMs online.

Best practice:

- Build your own VMs when possible
- Be cautious with downloaded VMs
- Know what software is inside before you trust them

### Virtual Desktop Infrastructure (VDI)

**VDI** means the desktop itself runs as a virtual machine on a remote system, often over the network or in the cloud.

You may also hear **DaaS**, Desktop as a Service.

On the local desk, the user mainly needs:

- Keyboard
- Mouse
- Display

Most processing, memory, and storage happen on the remote virtual desktop. The local device mainly receives screen updates and sends input, so network bandwidth matters.

From the user’s point of view, it still feels like a normal desktop OS.

### Containerization

Full VMs include a complete guest OS, which adds overhead.

**Containerization** virtualizes applications more lightly.

With containers:

- Each app runs in its own container
- Containers are isolated from each other unless configured otherwise
- Containers share one host operating system
- Images are smaller, faster to move, and more portable

Popular container software includes **Docker**.

#### VM vs Container

| Approach | OS Model | Size / Overhead | Flexibility |
| --- | --- | --- | --- |
| Virtual machine | Each VM has its own guest OS | Higher overhead | Different guest OSes on one host |
| Container | Apps share one host OS | Lightweight and portable | Usually must match the host OS family |

Trade-off:

- VMs can run different guest operating systems more freely
- Containers are lighter, but generally rely on the same host OS type

## Common Mix-Ups

### Type 1 vs Type 2

- Type 1 = on bare metal
- Type 2 = on a host OS

### VM vs Container

- VM = full guest OS
- Container = shares host OS, much lighter

### Bridged vs NAT

- Bridged = VM sits on the local network
- NAT / shared = VM uses translated access through the hypervisor

### VDI vs Local Desktop

- Local desktop = OS runs on the computer in front of you
- VDI = OS runs remotely; local device mainly displays it
