# Document Types

CompTIA A+ Core 2 — 220-1202  
Objective 4.1 — Given a scenario, implement best practices associated with documentation and support systems

## What You Need to Know

By the end of this lesson, you should understand:

- **Incident reports** and why they matter after problems
- **Standard operating procedures (SOPs)**
- **Onboarding** and **offboarding** documentation
- **Service level agreements (SLAs)** — external and internal
- **Knowledge bases** (vendor and in-house)

## What Is It?

IT runs on written playbooks — not memory. **Document types** are the standard papers and systems orgs use to record incidents, run day-to-day work, bring people in and out, promise service levels, and store known fixes.

## Why Does It Matter?

Without the right docs:

- Incidents repeat because nobody captured what worked
- Remote sites and new techs guess instead of following a process
- New hires wait days for accounts and gear
- Exiting employees leave data and assets in limbo
- Vendor uptime promises are unclear
- Good fixes stay trapped in one person’s head

## Real-World Analogy

Think of IT docs like a restaurant:

| Document | Kitchen equivalent |
| --- | --- |
| Incident report | Write-up after a kitchen fire — cause, response, leftover risk |
| SOP | Recipe and closing checklist |
| Onboarding | New cook setup: badge, station, knife kit |
| Offboarding | Returning keys, recipes, and locker contents |
| SLA | Contract with the food supplier: delivery times or you get a credit |
| Knowledge base | Searchable binder of “we already fixed this once” |

## How It Works

### Incident Reports

Created whenever a significant **incident** occurs.

Usually cover:

1. What led up to the incident  
2. What the incident was  
3. How the organization responded  

Tied to a formal **incident response plan** that says what to do when something happens. Over time, reports form a history you can analyze to **prevent repeats**.

### Standard Operating Procedures (SOPs)

Documented processes for how *this* organization does work — so anyone (help desk or remote site) follows the same steps.

| Example situation | SOP answers |
| --- | --- |
| Downtime | Who to contact first to fix it? Who to notify that it’s down? |
| Facilities / power loss at a remote site | Internal contacts + utility company contacts |
| Software install | Custom install steps |
| Day-to-day | App testing, change control, other standing processes |

Key idea: **predefined and available** before you need it.

### Onboarding Documentation

Processes so a new employee can work on **day one**.

Often includes:

| Item | Purpose |
| --- | --- |
| Signed agreements | Handbook acknowledgment and/or separate **Acceptable Use Policy (AUP)** |
| Account creation | New accounts; rights/permissions; correct groups and departments |
| Equipment | Laptop, tablet, desktop, or other gear required for the job |

### Offboarding Documentation

Defined **before** someone leaves — used the moment they are no longer an employee.

| Focus | Questions the procedure answers |
| --- | --- |
| Hardware / assets | How are laptop, phone, desktop recovered and tracked? |
| Data | Backed up? Handed off? Encrypted with keys the org still has? |

Goal: don’t lose critical data or leave accounts/assets hanging.

### Service Level Agreements (SLAs)

An **SLA** sets minimum service terms — usually with a provider, sometimes **internally** (e.g. IT vs another department).

| Type | Example |
| --- | --- |
| External | ISP contract: uptime, response time |
| Internal | Minimum expectations when working with IT |

**Sample ISP SLA terms:**

- No more than **four hours** unscheduled downtime per year (or credit / penalty)
- Technician dispatched after long outages
- Customer may need **spare equipment on site** so repairs are fast

### Knowledge Base (KB)

Searchable technical how-to for hardware, software, and local quirks.

| Source | Example |
| --- | --- |
| Vendor / external | Microsoft KB; third-party support sites |
| Institutional (in-house) | Custom apps and “how we do it here” |
| Help desk integration | Articles surface inside tickets to speed resolution |

Old articles can still save new tickets a year later.

## Side-by-Side Comparison

| Document | Main job |
| --- | --- |

## Common Mix-Ups

### SOP = SLA

SOP = **how we work**. SLA = **promised service levels** (often contractual).

### Offboarding is “delete everything”

Protect and hand off data first; recover assets; follow the written process.

### Knowledge base is only for Microsoft

Vendors *and* your company’s internal articles both count.

### Incident report is optional “nice to have”

It feeds prevention and matches the incident response plan.
